## Data Governance: Ownership, Access & Compliance

**Data governance is the set of processes, policies, and roles that make data discoverable, trusted, secure, and compliant as a platform scales beyond a single team.**

## Key Concepts

Governance starts with clear ownership: a **data owner** is accountable for a dataset's business meaning, a **data steward** maintains its quality and metadata day to day, and a **data custodian** operates the underlying platform. On top of ownership sits access control — **RBAC** grants permissions to roles, while **ABAC** evaluates dynamic attributes (department, region, sensitivity) for more flexible but harder-to-manage policies — plus finer-grained row- and column-level security for multi-tenant and PII-heavy datasets. A **data catalog** ties it together by making datasets discoverable, with lineage, owners, and freshness in one place, while a **business glossary** aligns what terms actually mean. Governance also has to answer compliance questions: how PII/PHI gets masked or tokenized, how access is audited, how GDPR deletion requests get honored across raw and derived layers, and how retention policies get enforced with expiry and lifecycle rules.

## Interview Questions

<QuestionList topic="Data Governance" storagePrefix="data-governance">

<QuestionCard id="dg-01" number={1} question="What is data governance and why does it matter?" difficulty="easy" topic="Fundamentals">
Data governance is the set of processes, policies, and responsibilities that ensure data is discoverable, trusted, secure, and used correctly. It matters because data platforms scale to many teams; without governance, definitions diverge, access becomes risky, and compliance issues appear. Good governance enables faster, safer self-service analytics.
</QuestionCard>

<QuestionCard id="dg-02" number={2} question="What is the difference between governance and security?" difficulty="medium" topic="Fundamentals">
Security focuses on preventing unauthorized access and ensuring confidentiality/integrity (access controls, encryption). Governance includes security but also covers ownership, definitions, quality, lifecycle, and change management. Governance answers "who owns this data and what does it mean," not just "who can access it."
</QuestionCard>

<QuestionCard id="dg-03" number={3} question="What are common roles in data governance (owner/steward/custodian)?" difficulty="easy" topic="Roles">
Common roles are:

- **data owner** — accountable for the dataset and its business definition
- **data steward** — maintains quality, metadata, and processes
- **data custodian** — operates the technical platform (storage, access, backups)

Clear roles prevent "nobody owns it" incidents.
</QuestionCard>

<QuestionCard id="dg-04" number={4} question="What is a data catalog and what should it contain?" difficulty="easy" topic="Cataloging">
A data catalog is an inventory of datasets with searchable metadata. It typically contains dataset descriptions, owners, lineage, classifications, freshness/SLA, schema, and links to dashboards. A good catalog reduces time to discovery and improves trust and reuse.
</QuestionCard>

<QuestionCard id="dg-05" number={5} question="What is business glossary vs. technical metadata?" difficulty="medium" topic="Metadata">
A business glossary defines business terms (for example "active user," "net revenue") and their approved definitions. Technical metadata describes datasets and fields (schemas, types, partitions, lineage). Both are needed: glossary aligns meaning, technical metadata enables implementation and discovery.
</QuestionCard>

<QuestionCard id="dg-06" number={6} question="RBAC vs. ABAC: what is the difference?" difficulty="medium" topic="Access Control">
RBAC (Role-Based Access Control) grants permissions to roles (analyst, engineer) and assigns users to roles. ABAC (Attribute-Based Access Control) uses attributes (department, region, sensitivity) to evaluate policies dynamically. ABAC is more flexible but can be harder to manage without good tooling.
</QuestionCard>

<QuestionCard id="dg-07" number={7} question="What is row-level and column-level security?" difficulty="medium" topic="Access Control">
Row-level security restricts which rows a user can see (for example only their region). Column-level security restricts which columns are visible (for example hide salary or PII). These controls are important for multi-tenant analytics and compliance.
</QuestionCard>

<QuestionCard id="dg-08" number={8} question="How do you handle PII/PHI data in analytics platforms?" difficulty="hard" topic="Compliance">
You classify sensitive fields, minimize exposure, and enforce least privilege. Common controls include encryption, masking/tokenization, column-level access, and auditing. You also ensure downstream marts only include necessary fields and implement secure sharing patterns.
</QuestionCard>

<QuestionCard id="dg-09" number={9} question="What is data masking and tokenization?" difficulty="medium" topic="Compliance">
Masking hides sensitive values (for example showing only the last 4 digits) while keeping the dataset usable. Tokenization replaces sensitive values with tokens that can be detokenized only with access to a secure mapping. Tokenization is useful when analytics needs stable identifiers without exposing raw PII.
</QuestionCard>

<QuestionCard id="dg-10" number={10} question="How do you implement auditability for data access?" difficulty="medium" topic="Auditing">
You log access events (who queried what, when, from where) and retain logs per policy. You also track permission changes and administrative actions. Audit logs should be queryable for investigations and compliance reporting.
</QuestionCard>

<QuestionCard id="dg-11" number={11} question="How do you handle GDPR “right to be forgotten” in a lakehouse/warehouse?" difficulty="hard" topic="Compliance">
You need a process to delete or anonymize personal data across raw, derived, and serving layers. This can involve targeted deletes (where supported), reprocessing from raw logs without the user, or storing personal data separately to allow deletion without rewriting large datasets. You also document what is feasible given retention and legal constraints.
</QuestionCard>

<QuestionCard id="dg-12" number={12} question="What are data retention policies and how do you enforce them?" difficulty="medium" topic="Retention">
Retention policies define how long data is kept and when it must be deleted or archived. Enforcement can be implemented with partition expiry jobs, lifecycle rules on object storage, snapshot expiration, and access reviews. Retention must align with legal requirements and business needs.
</QuestionCard>

</QuestionList>

## Classification & Modern Governance Models

How sensitivity gets labeled, and how governance changes shape once a platform grows past one central team.

<QuestionList topic="Classification & Modern Models" storagePrefix="dg-modern">

<QuestionCard id="dg-13" number={13} question="What is data classification, and what tiers does a typical scheme use?" difficulty="easy" topic="Classification">
Data classification labels datasets (or individual columns) by sensitivity, so access controls, masking rules, and retention policies can be applied consistently based on that label rather than decided ad hoc per table. A common scheme: **Public** (no restriction), **Internal** (company-only), **Confidential** (restricted to specific teams/roles), and **Restricted** (PII/PHI, tightest controls, often legally regulated) — each tier mapping to a concrete, enforced set of access and handling rules.
</QuestionCard>

<QuestionCard id="dg-14" number={14} question="What is data mesh, and how does it change the governance model compared to a centralized team?" difficulty="hard" topic="Data Mesh">
Data mesh distributes data ownership to the domain teams that actually produce the data (treating each domain's output as a "data product" they're responsible for), instead of a single central data team owning ingestion, quality, and governance for everything. Governance shifts from "the central team enforces every rule" to **federated computational governance** — global standards (security, compliance, interoperability) are defined centrally, but enforced automatically through shared tooling/platforms, while domain-specific decisions stay with the domain teams.
</QuestionCard>

<QuestionCard id="dg-15" number={15} question="What is federated computational governance in a data mesh?" difficulty="hard" topic="Data Mesh">
It's the mechanism that keeps a decentralized data mesh from becoming ungoverned chaos: a small set of global rules (schema standards, security policies, PII handling) are defined once by a federated group (representatives from each domain, not one central authority), then **enforced automatically** by the platform itself — automated policy checks, standardized catalog registration — rather than manually policed for every domain's every dataset.
</QuestionCard>

<QuestionCard id="dg-16" number={16} question="What's the difference between anonymization and pseudonymization?" difficulty="hard" topic="Compliance">
**Anonymization** irreversibly removes the ability to re-identify an individual — done correctly, the data falls outside the scope of regulations like GDPR entirely, but it's often destructive to analytical value and genuinely hard to guarantee (re-identification via combining "anonymized" fields is a known risk). **Pseudonymization** replaces identifying fields with a token or key, but the mapping back to the real identity still exists somewhere — it reduces risk and is often required by regulation, but the data is still considered personal data because re-identification remains possible.
</QuestionCard>

<QuestionCard id="dg-17" number={17} question="What is a data product, and how does governance apply differently to it than to a raw table?" difficulty="medium" topic="Data Mesh">
A data product is a dataset treated with the same discipline as a customer-facing product: it has a defined owner, a documented interface (schema/contract), quality SLAs, and discoverability — not just "a table that happens to exist." Governance for a data product is largely self-contained and owned by the producing domain (they're accountable for its contract and quality), whereas governance for an ungoverned raw table typically falls back to whatever central policy applies by default, with no one specifically accountable for its fitness for use.
</QuestionCard>

</QuestionList>

## Tooling & Automation

Turning governance from documented policy into something the platform actually enforces.

<QuestionList topic="Tooling & Automation" storagePrefix="dg-tooling">

<QuestionCard id="dg-18" number={18} question="What do data catalog tools like DataHub or Collibra actually provide beyond a spreadsheet of tables?" difficulty="medium" topic="Tooling">
They automatically ingest metadata (schemas, ownership, usage stats) directly from the warehouse/pipelines rather than relying on someone to manually maintain a document, so the catalog doesn't silently go stale the way a spreadsheet does. They also add lineage graphs connecting datasets to their upstream/downstream dependencies, search and discovery, and often plug into access-request workflows and classification tagging — turning a static inventory into a live, queryable system of record.
</QuestionCard>

<QuestionCard id="dg-19" number={19} question="What is policy-as-code, and how does it apply to access governance?" difficulty="hard" topic="Automation">
```yaml
# example: an access policy defined declaratively, not granted manually
policy: deny
  if: resource.classification == "restricted"
     and not user.has_role("data-steward")
```
Policy-as-code defines access rules as version-controlled, testable configuration (often using a tool like Open Policy Agent) rather than permissions granted manually through a UI. This makes access policy reviewable in the same pull-request process as any other code change, consistently enforced across every system that respects it, and auditable — you can see exactly when and why a rule changed, not just infer it from who currently has access.
</QuestionCard>

<QuestionCard id="dg-20" number={20} question="How would you automate detection of PII in a dataset you didn't design?" difficulty="medium" topic="Automation">
Combine pattern-based scanning (regexes for emails, SSNs, phone numbers, credit card formats) with column-name heuristics (`email`, `ssn`, `dob`) and, for higher confidence, a trained classifier on sampled values. Automated scanning is a starting point, not a final answer — it needs a human review step for ambiguous cases, since it will both miss context-dependent PII and occasionally flag something that isn't (a column named `user_id` that's actually a random UUID, not identifying on its own).
</QuestionCard>

<QuestionCard id="dg-21" number={21} question="What is an access request/approval workflow, and why not just grant broad access upfront?" difficulty="easy" topic="Access Control">
An access request workflow requires someone to explicitly request access to a specific dataset, with an owner or steward approving it (often time-bound, sometimes requiring a business justification), rather than everyone getting broad default access. Granting broad access upfront is simpler operationally but violates least-privilege — it makes audits meaningless (everyone can see everything, so "who accessed this" tells you nothing useful) and makes revoking access when someone changes teams or leaves nearly impossible to reason about.
</QuestionCard>

</QuestionList>

## Compliance Frameworks & Process

Beyond GDPR — comparing regulatory regimes, and the organizational processes that make governance stick.

<QuestionList topic="Compliance & Process" storagePrefix="dg-compliance">

<QuestionCard id="dg-22" number={22} question="How does GDPR differ from CCPA from a data engineering perspective?" difficulty="hard" topic="Compliance">
Both require honoring deletion and access requests, but **GDPR** (EU) is opt-in by default (you generally need a lawful basis and often explicit consent to process personal data at all) and applies more broadly to "personal data." **CCPA** (California) is more opt-out oriented (processing is generally allowed unless the consumer opts out, particularly of *sale* of their data) and is narrower in some respects but still requires similar underlying capabilities — knowing what personal data you hold about someone and being able to delete or export it on request.
</QuestionCard>

<QuestionCard id="dg-23" number={23} question="What is consent management, and how does it affect what a pipeline is allowed to process?" difficulty="medium" topic="Compliance">
Consent management tracks what each user has actually agreed to (marketing use, analytics, third-party sharing) as its own structured, queryable data — not just a one-time checkbox that's forgotten. A pipeline that ingests or transforms personal data needs to check current consent state before processing for a given purpose, and needs to handle consent being **withdrawn** after the fact, which usually means the same deletion/reprocessing machinery used for a "right to be forgotten" request.
</QuestionCard>

<QuestionCard id="dg-24" number={24} question="What is a Data Protection Impact Assessment (DPIA), and when is one required?" difficulty="hard" topic="Compliance">
A DPIA is a structured assessment of the privacy risk a new system or process introduces before it launches — what personal data it touches, what could go wrong, and what mitigations are in place — required under GDPR for processing likely to result in high risk to individuals (large-scale sensitive data processing, systematic profiling). For a data engineering team, this means privacy review becomes a design-time gate for certain new pipelines, not something bolted on after the fact.
</QuestionCard>

<QuestionCard id="dg-25" number={25} question="How do you measure whether a governance program is actually working?" difficulty="medium" topic="Governance Maturity">
Track concrete, observable signals rather than "we wrote a policy document": percentage of datasets with an assigned owner and complete catalog metadata, time-to-fulfill for access requests and deletion requests, number of datasets with an enforced classification tag, and audit findings from access reviews. A governance program with no metrics is one nobody can tell is failing until an incident (a compliance violation, a "nobody owns this" fire drill) forces the question.
</QuestionCard>

<QuestionCard id="dg-26" number={26} question="How would you design a RACI matrix for a new data domain?" difficulty="medium" topic="Process">
A RACI matrix maps each governance activity (defining the schema, approving access, responding to a quality incident, honoring a deletion request) to who is **R**esponsible (does the work), **A**ccountable (final approval, usually the data owner), **C**onsulted (has input beforehand), and **I**nformed (told after the fact) — for a new domain, this is worth doing explicitly up front specifically to avoid the common failure mode where an incident happens and three teams each assume another team owns the response.
</QuestionCard>

</QuestionList>

## Common Interview Scenarios

- **"A new analyst asks to see raw customer PII 'just to debug a report' — how do you respond?"** Tests least privilege, masking/tokenization, and role boundaries.
- **"Legal asks you to delete a specific user's data across the entire warehouse for a GDPR request — walk through your approach."** Tests the raw/derived layer deletion strategy and audit trail.
- **"Two teams have different definitions of 'active user' in their dashboards — how do you fix that at the platform level?"** Tests business glossary thinking and conformed definitions.
- **"Design the ownership model for a new data domain with three producing teams and ten consuming teams."** Tests owner/steward/custodian role design.
- **"Your company is moving from a central data team to a data mesh model — what changes about governance?"** Tests federated computational governance thinking: which rules stay centrally enforced (security, compliance, interoperability standards) versus which decisions move to the domain teams now accountable as data product owners.
- **"How would you prove to an auditor that access to a restricted dataset is actually controlled, not just documented?"** Tests policy-as-code and access-request-workflow thinking — pointing to enforced, version-controlled rules and a queryable request/approval trail, not a policy document nobody checks against reality.
