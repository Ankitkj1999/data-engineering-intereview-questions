## Data Quality: Accuracy, Completeness & Trust

**Data quality is the practice of ensuring data is correct, complete, consistent, and timely enough that downstream consumers can trust it — a mix of pipeline engineering (checks, contracts, monitoring) and product thinking (clear definitions and ownership).**

## Key Concepts

Data quality means data is fit for its intended use, which usually breaks down into six dimensions: completeness, validity, accuracy, consistency, timeliness/freshness, and uniqueness. Checks operate at two levels — **row-level checks** (`not_null`, regex, range constraints on individual records) and **aggregate checks** (row counts, distinct counts, distribution shifts across the whole dataset) — and both are needed because aggregate checks catch issues row-level rules miss, like a missing partition. Upstream, **data contracts** and schema-drift detection prevent producers from silently breaking consumers; downstream, **quarantine patterns** let bad rows get isolated with an error reason while the pipeline keeps running for valid data. A common failure mode is alert fatigue, so mature setups lean on dynamic thresholds and multi-signal alerting (freshness + volume + error rate) rather than single noisy checks.

## Interview Questions

<QuestionList topic="Data Quality" storagePrefix="data-quality">

<QuestionCard id="dq-01" number={1} question="What does data quality mean in data engineering?" difficulty="easy" topic="Fundamentals">
Data quality means the data is fit for its intended use. In practice, it means data is correct, complete, consistent, timely, and well-defined so downstream consumers can trust metrics. Data quality is both a technical problem (pipelines) and a product problem (definitions and contracts).
</QuestionCard>

<QuestionCard id="dq-02" number={2} question="What are common dimensions of data quality?" difficulty="easy" topic="Fundamentals">
Common dimensions include:

- completeness (missing rows/fields)
- validity (values in allowed ranges/domains)
- accuracy (matches real-world or source truth)
- consistency (no contradictions across tables)
- timeliness/freshness (arrives within SLA)
- uniqueness (no duplicates where keys should be unique)
</QuestionCard>

<QuestionCard id="dq-03" number={3} question="What is data freshness and how do you measure it?" difficulty="easy" topic="Freshness">
Freshness is how recently data was updated relative to expected cadence. You can measure it by comparing the maximum event/ingestion timestamp in a table to current time, and alert when it exceeds an SLA threshold. Freshness should be defined per dataset because "daily" and "real-time" pipelines differ.
</QuestionCard>

<QuestionCard id="dq-04" number={4} question="What is the difference between data validation and data reconciliation?" difficulty="medium" topic="Validation">
Validation checks whether a dataset satisfies rules (types, constraints, ranges). Reconciliation compares datasets to ensure they match expected totals or invariants (for example source row count vs. target row count, or `sum(amount)` in source vs. warehouse). Reconciliation is important when multiple systems can drift.
</QuestionCard>

<QuestionCard id="dq-05" number={5} question="What are row-level checks and aggregate checks?" difficulty="medium" topic="Checks">
Row-level checks validate each record (for example `not_null`, regex, range constraints). Aggregate checks validate the dataset as a whole (row counts, distinct counts, distribution checks, totals). Aggregate checks often catch issues that row-level rules miss, like missing partitions.
</QuestionCard>

<QuestionCard id="dq-06" number={6} question="How do you design quality checks for incremental pipelines?" difficulty="hard" topic="Pipelines">
Checks should be scoped to the incremental window and also protect the full table invariants. For example, validate uniqueness on the keys in the new batch, validate that the batch size is within expected bounds, and validate that total counts change consistently. You also need idempotency checks to detect duplicates on retries.
</QuestionCard>

<QuestionCard id="dq-07" number={7} question="How do you handle late arriving data from a quality perspective?" difficulty="hard" topic="Pipelines">
You define allowed lateness (for example 7 days), track completeness by event time, and implement backfills to "close" historical partitions. Quality checks should consider both ingestion time and event time so you can detect gaps in past periods.
</QuestionCard>

<QuestionCard id="dq-08" number={8} question="How do you detect schema drift and breaking changes?" difficulty="medium" topic="Schema">
You compare incoming schemas to an expected contract (column names, types, nullability) and alert on changes. Additive changes can be allowed with policy, but breaking changes (rename/type change) should fail fast. Many teams use CI checks and schema registries to enforce compatibility.
</QuestionCard>

<QuestionCard id="dq-09" number={9} question="What are data contracts?" difficulty="medium" topic="Contracts">
Data contracts are explicit agreements between producers and consumers about schema, semantics, SLAs, and ownership. Contracts reduce surprises by defining what can change and what cannot, and they enable automated validation. A contract can live as code (YAML/JSON) and be enforced in CI/CD.
</QuestionCard>

<QuestionCard id="dq-10" number={10} question="How do you avoid noisy alerts (false positives) in data quality monitoring?" difficulty="medium" topic="Alerting">
Use dynamic thresholds, seasonality-aware baselines, and multi-signal alerts (freshness + volume + error rate). Also route alerts by severity and dataset criticality, and suppress alerts during known maintenance windows. Good alerting includes a runbook and clear ownership.
</QuestionCard>

<QuestionCard id="dq-11" number={11} question="What is anomaly detection for metrics and when is it useful?" difficulty="medium" topic="Monitoring">
Anomaly detection flags unusual changes in metrics (spikes/drops) that may indicate pipeline issues or business events. It is useful for detecting silent failures where data still arrives but is wrong. It should be combined with context (releases, campaigns) to avoid alert fatigue.
</QuestionCard>

<QuestionCard id="dq-12" number={12} question="How do you quarantine bad data without blocking the entire pipeline?" difficulty="hard" topic="Pipelines">
A common pattern is to split data into "good" and "quarantine" outputs based on validation rules. You can store bad rows with error reasons for debugging while allowing the pipeline to continue for valid data. For critical datasets, you may still block publishing to marts while keeping raw ingestion running.
</QuestionCard>

<QuestionCard id="dq-13" number={13} question="How do you test data transformations?" difficulty="medium" topic="Testing">
You can test transformations by:

- unit-like tests on small fixtures (golden datasets)
- property tests (invariants like non-negative totals)
- reconciliation tests against known sources
- regression tests on key metrics

In dbt-style workflows, tests often run in the warehouse as SQL assertions.
</QuestionCard>

<QuestionCard id="dq-14" number={14} question="What is the minimum set of checks you would add to every table?" difficulty="easy" topic="Checks">
Minimum checks often include:

- freshness (max timestamp within SLA)
- row count / volume sanity check
- primary key uniqueness (if applicable)
- not_null checks on critical columns
- referential integrity for key joins (where applicable)
</QuestionCard>

<QuestionCard id="dq-15" number={15} question="What are common data quality failure modes?" difficulty="medium" topic="Failure Modes">
Common failures include:

- missing partitions or partial loads
- duplicates due to retries/reprocessing
- schema drift and type coercion issues
- timezone and date boundary bugs
- silent truncation or rounding changes
- incorrect joins causing duplication
</QuestionCard>

</QuestionList>

## Tooling & Frameworks

The actual libraries and workflows teams use to define and run checks, rather than writing ad-hoc validation SQL every time.

<QuestionList topic="Tooling & Frameworks" storagePrefix="dq-tools">

<QuestionCard id="dq-16" number={16} question="What is Great Expectations, and what problem does it solve?" difficulty="medium" topic="Tooling">
Great Expectations is a Python framework for defining data quality rules ("expectations" — `expect_column_values_to_not_be_null`, `expect_column_values_to_be_between`) as declarative, version-controllable code rather than one-off SQL scripts. Expectations are grouped into **suites** and run via **checkpoints**, producing a human-readable validation report — it solves the problem of quality checks living as tribal knowledge or scattered scripts by making them a first-class, testable, shareable artifact.
</QuestionCard>

<QuestionCard id="dq-17" number={17} question="How do dbt's built-in tests (unique, not_null, relationships, accepted_values) work?" difficulty="easy" topic="Tooling">
```yaml
models:
  - name: orders
    columns:
      - name: order_id
        tests: [unique, not_null]
      - name: status
        tests:
          - accepted_values: {values: ["pending", "shipped", "cancelled"]}
      - name: customer_id
        tests:
          - relationships: {to: ref('customers'), field: customer_id}
```
Each test compiles to a SQL query that should return **zero rows** if the data is valid — `dbt test` runs them after a build and fails the run if any query returns rows. They're declared alongside the model definition, so the quality rule lives right next to the transformation it's validating.
</QuestionCard>

<QuestionCard id="dq-18" number={18} question="When would you choose a dedicated framework like Great Expectations over dbt tests?" difficulty="medium" topic="Tooling">
dbt tests are ideal when checks are simple, SQL-expressible, and already living inside a dbt project — low friction, no extra tooling. Reach for Great Expectations (or a similar dedicated framework) when you need checks outside a dbt-managed warehouse (raw files, a data lake, a non-dbt pipeline), richer statistical expectations, or standalone validation reports/documentation independent of any single transformation tool.
</QuestionCard>

<QuestionCard id="dq-19" number={19} question="How do you integrate data quality checks into a CI/CD pipeline?" difficulty="medium" topic="Tooling">
Run checks against a representative sample or a full staging dataset as part of the build/deploy pipeline — for dbt, `dbt build` runs models and tests together, failing the pipeline before a broken model reaches production. The key design decision is *what blocks deployment versus what just alerts*: schema-breaking changes and critical table failures should block merges, while softer statistical checks (mild distribution shifts) are often better as warnings that don't halt every deploy.
</QuestionCard>

<QuestionCard id="dq-20" number={20} question="What is data profiling, and why is it the first step before writing quality checks for a new dataset?" difficulty="easy" topic="Profiling">
Profiling means computing summary statistics on a dataset before you know what to check — null rates per column, distinct value counts, min/max/mean, common patterns in string columns. It matters because you can't write meaningful checks (what's a "normal" null rate? what values are actually valid?) without first understanding what the data actually looks like; skipping profiling leads to either checks that are too loose to catch real problems or so strict they fail on legitimate data.
</QuestionCard>

</QuestionList>

## Practical Validation Techniques

Specific problems that come up once you move past "check for nulls" into real production datasets.

<QuestionList topic="Practical Validation Techniques" storagePrefix="dq-practical">

<QuestionCard id="dq-21" number={21} question="How do you check referential integrity in a warehouse that doesn't enforce foreign keys?" difficulty="medium" topic="Referential Integrity">
Most analytical warehouses accept (but don't enforce) foreign key declarations, so referential integrity has to be checked explicitly — typically an anti-join: rows in the child table whose key doesn't exist in the parent table.

```sql
SELECT o.customer_id
FROM orders o
LEFT JOIN customers c ON o.customer_id = c.customer_id
WHERE c.customer_id IS NULL   -- orphaned foreign keys
```

Run this as a scheduled check (or a dbt `relationships` test) rather than relying on the database to reject bad writes, since the warehouse itself won't.
</QuestionCard>

<QuestionCard id="dq-22" number={22} question="What techniques do you use to detect duplicate records at scale?" difficulty="hard" topic="Deduplication">
For exact duplicates, hash the row's relevant columns and check for repeated hash values — cheaper than comparing every column pairwise. For duplicates that differ slightly (a retry that changed a timestamp), define a business key (the columns that should uniquely identify a record) and check *that* for uniqueness instead of the whole row. At large scale, a window function is the standard SQL pattern for both detecting and resolving duplicates:

```sql
SELECT *, ROW_NUMBER() OVER (PARTITION BY business_key ORDER BY updated_at DESC) AS rn
FROM table
QUALIFY rn = 1   -- keep only the most recent version of each key
```
</QuestionCard>

<QuestionCard id="dq-23" number={23} question="How do you detect distribution drift in a column's values over time?" difficulty="hard" topic="Statistical Checks">
Compare a statistical summary of today's batch against a rolling historical baseline — mean/median/standard deviation for numeric columns, or the distribution of category frequencies for categorical ones — and alert when the difference exceeds a threshold (a fixed percentage, or a statistical distance measure like population stability index for more rigorous setups). This catches problems row-level checks can't: every row can individually be "valid" while the overall shape of the data has still shifted in a way that signals an upstream change.
</QuestionCard>

<QuestionCard id="dq-24" number={24} question="What data quality challenges are unique to streaming pipelines compared to batch?" difficulty="hard" topic="Streaming">
Batch checks run against a complete, stable dataset; streaming checks have to work against data that's still arriving, with no natural "batch is done" moment to validate against. This means checks need to run over rolling windows rather than a fixed dataset, tolerate legitimately late/out-of-order events without false-alarming, and use approximate techniques (sketches for distinct counts, running aggregates) since holding the full stream in memory to validate it isn't an option.
</QuestionCard>

<QuestionCard id="dq-25" number={25} question="How do you decide between NULL, an empty string, and a sentinel value for missing data?" difficulty="medium" topic="Data Modeling">
Use **NULL** for "value doesn't exist / unknown," reserving it for genuine absence rather than overloading it with multiple meanings. Use an **empty string** only when "known to be empty" is itself meaningful and distinct from "unknown" (a middle name field where you've confirmed the person has none, vs. one you simply haven't collected). Avoid ad-hoc **sentinel values** ("N/A", -1, 9999) in the data itself wherever possible — they're invisible to standard NULL-handling logic (COUNT, aggregates, joins) and silently corrupt results unless every downstream consumer knows to filter them out; if you need a placeholder in a dimension for exactly this reason, use the "Unknown member" pattern instead.
</QuestionCard>

<QuestionCard id="dq-26" number={26} question="Where in a medallion (bronze/silver/gold) pipeline should quality gates actually enforce checks?" difficulty="medium" topic="Pipeline Design">
Light structural checks (can it be parsed, does it match the expected raw schema) belong at bronze, right on ingestion, so malformed source data is caught immediately rather than propagating. The bulk of validation — not-null, referential integrity, business rules, deduplication — belongs at the bronze-to-silver transition, since silver is meant to be the clean, trusted layer everything else builds on. Gold-layer checks are usually reconciliation-style (do these aggregates tie back to silver correctly) rather than re-validating row-level rules that should have already been caught upstream.
</QuestionCard>

</QuestionList>

## Metrics, Ownership & Trust

Beyond individual checks — how you decide how much quality investment a dataset deserves, and who's responsible when it fails.

<QuestionList topic="Metrics, Ownership & Trust" storagePrefix="dq-trust">

<QuestionCard id="dq-27" number={27} question="How do you build a data quality score, and what would it be based on?" difficulty="medium" topic="Metrics">
A simple, defensible approach: weight each quality dimension (completeness, validity, freshness, uniqueness) by how much it matters for that specific dataset, compute a pass rate for each from your existing checks, and combine into a single 0-100 score per table. The value isn't the exact number — it's giving stakeholders a trend line ("this table's score dropped from 98 to 85 last week") that's easier to act on than a wall of individual pass/fail check results.
</QuestionCard>

<QuestionCard id="dq-28" number={28} question="How do you decide how much quality investment a dataset actually needs?" difficulty="medium" topic="Prioritization">
Scale checks to the dataset's actual blast radius: a table feeding an executive dashboard or a financial report justifies deep validation, reconciliation, and tight SLAs; an internal exploratory table a few analysts use occasionally doesn't need the same investment. Treating every table as equally critical is how quality programs burn effort on low-value checks while genuinely important tables stay under-covered — usage and downstream dependency count are the practical signals for where to spend the effort.
</QuestionCard>

<QuestionCard id="dq-29" number={29} question="Who should own a data quality failure — the producing team or the consuming team?" difficulty="medium" topic="Ownership">
The producing team owns fixing the *source* of the problem (a broken upstream job, a schema change that wasn't communicated), since they're the only ones who can actually correct it at the root. The consuming team typically owns detecting and surfacing the failure fast (their checks, their dashboards break first) and communicating impact — a data contract is what ties these together in advance, so this isn't negotiated fresh during every incident.
</QuestionCard>

<QuestionCard id="dq-30" number={30} question="How do you build stakeholder trust in data after a high-profile quality incident?" difficulty="medium" topic="Trust">
Be transparent about what happened and why, rather than quietly fixing it — a short incident writeup (what broke, what was affected, what's changing) does more for trust than silence. Follow up with a durable fix (a new check that would have caught it, not just a one-time patch), and make quality *visible* going forward — a quality score, a status page, or a badge on documented tables — so trust is rebuilt on demonstrated reliability over time rather than a single reassurance.
</QuestionCard>

</QuestionList>

## Common Interview Scenarios

- **"A dashboard's revenue number dropped 20% overnight — walk me through how you'd investigate."** Tests freshness/volume checks, anomaly detection, and reconciliation instincts.
- **"Design the minimum set of quality checks you'd add to a new fact table before it ships to production."** Tests knowledge of freshness, volume, primary key uniqueness, not-null, and referential integrity checks.
- **"A producing team wants to rename a column — how do you prevent that from breaking five downstream dashboards?"** Tests understanding of contracts, schema drift detection, and CI enforcement.
- **"Your quality checks are so noisy that the on-call engineer has started ignoring them — how do you fix that?"** Tests dynamic thresholds, multi-signal alerting, and clear ownership.
- **"You've inherited a table with no existing quality checks — where do you start?"** Tests the profiling-first instinct: understand null rates, distinct counts, and value ranges before writing a single check, then prioritize based on how critical and widely-used the table actually is.
- **"Two teams' dashboards show different revenue totals from what should be the same underlying data."** Tests reconciliation instincts and referential-integrity thinking — walk through checking for a duplicated join, a dropped filter, or an orphaned foreign key causing rows to silently disappear from one side.
