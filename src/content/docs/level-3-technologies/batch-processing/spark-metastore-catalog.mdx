## Metastore & Catalog Management: Tracking Metadata Across a Platform

**A catalog's whole value is letting `SELECT * FROM database.table` work without anyone remembering an S3 path — it's the layer that turns a pile of files in object storage into something that behaves like a real, queryable table.**

## Key Concepts

Without a catalog, "reading a table" means knowing its exact storage path and schema by heart. A catalog — the **Hive Metastore**, **AWS Glue Data Catalog**, or Databricks' **Unity Catalog** — stores that mapping centrally, so `database.table` resolves to the right location and schema automatically, and multiple engines (Spark, Presto/Athena, Redshift Spectrum) can share one source of truth instead of each maintaining their own. That metadata still has to reflect reality: **table discovery** tools (crawlers, `MSCK REPAIR TABLE`) exist specifically because storage and metadata can drift apart — new partitions land on disk that the catalog doesn't know about yet — and **schema registries** solve the same underlying problem for streaming data, where the "schema" isn't a static table definition but something evolving message by message.

## Hive Metastore Integration

<QuestionList topic="Hive Metastore Integration" storagePrefix="spark-metastore-hive">

<QuestionCard id="hmi-01" number={1} question="How does Spark integrate with the Hive Metastore, and what does enabling it actually change?" difficulty="medium" topic="Hive Metastore">
Enabling Hive support (`SparkSession.builder.enableHiveSupport()`, or `spark.sql.catalogImplementation = hive`) lets Spark read and write the same metastore Hive uses for table and partition metadata — once enabled, `spark.sql("SELECT * FROM database.table")` resolves against that shared metastore instead of Spark's default in-memory catalog, which only exists for the life of the current session.
</QuestionCard>

<QuestionCard id="hmi-02" number={2} question="What configuration does Spark need to locate an external Hive Metastore?" difficulty="medium" topic="Hive Metastore">
A `hive-site.xml` on Spark's classpath (or equivalent `spark.hadoop.hive.metastore.*` configuration) pointing at the metastore's connection details — typically the Thrift URI of a metastore service backed by an external database, the same configuration Hive itself would use to find its "Local Metastore" rather than an embedded, single-process one.
</QuestionCard>

<QuestionCard id="hmi-03" number={3} question="What does querying a table via database.table syntax rely on the metastore for?" difficulty="easy" topic="Hive Metastore">
The metastore resolves that name to the table's actual storage location, its schema (columns and types), its partition scheme, and its storage format/SerDe — everything needed to plan and execute the query — so the query never has to hardcode a physical path.
</QuestionCard>

</QuestionList>

For what the metastore itself stores and how embedded vs. external deployments differ, see [Hive](/level-3-technologies/batch-processing/hive/#metastore-data-types--data-model).

## AWS Glue Data Catalog Usage

<QuestionList topic="AWS Glue Data Catalog Usage" storagePrefix="spark-metastore-glue">

<QuestionCard id="agc-01" number={1} question="What is AWS Glue Data Catalog, and what problem does it solve for Spark on AWS?" difficulty="easy" topic="Glue Catalog">
A managed, Hive-metastore-compatible catalog service on AWS — it solves the same "table name to schema/location" problem the Hive Metastore does, but as a fully managed service, avoiding the need to stand up and operate a metastore database yourself.
</QuestionCard>

<QuestionCard id="agc-02" number={2} question="How does Spark (e.g., on EMR or Glue jobs) use the Glue Catalog instead of a Hive Metastore?" difficulty="medium" topic="Glue Catalog">
On EMR, a configuration flag (`hive.metastore.client.factory.class` set to the Glue catalog client) redirects Spark's Hive-compatible catalog calls to Glue instead of a self-managed metastore database — from the query-writing perspective, `database.table` syntax works identically either way, since Glue speaks the same Hive-compatible interface.
</QuestionCard>

<QuestionCard id="agc-03" number={3} question="Why is a shared catalog like Glue valuable across Spark, Athena, and Redshift Spectrum specifically?" difficulty="medium" topic="Glue Catalog">
All three can query the exact same tables, defined once, without each service needing its own separate metadata definition kept manually in sync — a table crawled or created once in Glue is immediately queryable from any of them, which is a meaningfully different operational story than maintaining parallel schema definitions per engine.
</QuestionCard>

</QuestionList>

## External Schema Registries

<QuestionList topic="External Schema Registries" storagePrefix="spark-metastore-schema-registry">

<QuestionCard id="esr-01" number={1} question="What is a schema registry, and why does it matter specifically for streaming/Avro pipelines?" difficulty="medium" topic="Schema Registries">
A schema registry (Confluent Schema Registry, AWS Glue Schema Registry) is a centralized service that stores and versions schemas — typically Avro or Protobuf — separately from the messages themselves. It matters for streaming because a continuous stream of messages has no natural place to embed a full schema per message cheaply, and producers/consumers need a shared, evolving contract without redeploying in lockstep.
</QuestionCard>

<QuestionCard id="esr-02" number={2} question="How does a Spark streaming consumer use a schema registry when reading Avro-encoded Kafka messages?" difficulty="medium" topic="Schema Registries">
Each message typically carries only a small schema ID rather than the full schema; the consumer looks up that ID against the registry to fetch the actual schema needed to deserialize the message — a Spark Structured Streaming job reading such a topic uses a registry-aware deserializer (via a connector library) to perform that lookup as part of decoding each batch.
</QuestionCard>

<QuestionCard id="esr-03" number={3} question="What problem does a schema registry solve that embedding the schema in every message wouldn't?" difficulty="medium" topic="Schema Registries">
Embedding a full schema in every message wastes significant bandwidth and storage at high message volume, and gives producers/consumers no centralized way to enforce compatibility rules as the schema evolves over time. A registry keeps messages small (just an ID) while still providing centralized schema versioning, compatibility checking, and a single place both sides can validate against independently.
</QuestionCard>

</QuestionList>

## Catalog Namespace Isolation

<QuestionList topic="Catalog Namespace Isolation" storagePrefix="spark-metastore-namespace">

<QuestionCard id="cni-01" number={1} question="What does catalog.database.table namespacing provide, and why does it matter at scale?" difficulty="medium" topic="Namespace Isolation">
It provides multiple independent naming scopes — different catalogs or databases can each define a table named `orders` without colliding, since the full three-part name disambiguates them. At scale, with many teams and environments sharing infrastructure, this prevents the kind of naming collision that a single flat namespace would eventually force.
</QuestionCard>

<QuestionCard id="cni-02" number={2} question="How does namespace isolation help prevent cross-team or cross-environment collisions?" difficulty="medium" topic="Namespace Isolation">
Separate catalogs or databases can represent separate teams, business domains, or environments (dev/staging/prod) — each free to define tables and schemas without needing to coordinate naming with every other group sharing the same underlying metastore/catalog service, and access control can be scoped at the catalog or database level to match those same boundaries.
</QuestionCard>

</QuestionList>

## Table Discovery and Metadata Sync

<QuestionList topic="Table Discovery and Metadata Sync" storagePrefix="spark-metastore-discovery">

<QuestionCard id="tds-01" number={1} question="What problem does a crawler, like AWS Glue Crawler, solve?" difficulty="easy" topic="Table Discovery">
A crawler scans actual storage (S3, HDFS) to detect data's structure and schema, then automatically creates or updates the corresponding catalog table definition — solving the problem of metadata not existing at all yet, or drifting out of date as new files/partitions land without anyone manually updating the catalog.
</QuestionCard>

<QuestionCard id="tds-02" number={2} question="What does MSCK REPAIR TABLE do, and when do you need to run it?" difficulty="medium" topic="Table Discovery">
It scans a table's storage location for partition directories that exist on disk but aren't yet registered in the metastore, and adds them — needed after new Hive-style partitioned data has been written directly to storage (e.g., by an external job) without going through a path that also updates the metastore automatically.
</QuestionCard>

<QuestionCard id="tds-03" number={3} question="What's the risk of metastore metadata drifting out of sync with actual storage?" difficulty="hard" topic="Table Discovery">
Queries can silently miss data that physically exists (new partitions the metastore doesn't know about yet aren't scanned at all) or fail/error against data the metastore claims exists but has since been moved or deleted — either way, the catalog's whole value proposition (a trustworthy map from table name to actual data) breaks down, which is why discovery/sync isn't a one-time setup step but an ongoing operational concern.
</QuestionCard>

</QuestionList>

## Common Interview Scenarios

- **"A newly landed partition isn't showing up in query results even though the files exist in S3 — why, and how do you fix it?"** Point to metastore/catalog drift, and the fix — running a crawler or `MSCK REPAIR TABLE` (or ensuring the write path itself registers new partitions automatically).
- **"Why would a team running Spark, Athena, and Redshift Spectrum all point at AWS Glue Data Catalog instead of each maintaining its own metadata?"** Discuss the single-source-of-truth benefit versus the operational cost of keeping several separate metadata definitions in sync manually.
- **"How would you design table namespacing for a company with 5 separate data teams sharing one Spark platform?"** A catalog/database-per-team (or per-domain) namespace isolation design, with access control scoped to match.
- **"A streaming pipeline reading Avro from Kafka needs to handle producers evolving their schema independently — how do you support that?"** A schema registry prompt, explaining how it decouples producer and consumer schema versions from needing to change in lockstep.
