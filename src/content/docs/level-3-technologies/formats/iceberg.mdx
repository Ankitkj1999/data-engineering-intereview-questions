## Apache Iceberg: Open Table Format

**Apache Iceberg is an open table format for large analytics datasets that adds transactional guarantees, consistent snapshots, and safe schema/partition evolution on top of files like Parquet — so multiple engines can read and write the same tables safely.**

## Key Concepts

Iceberg tracks table state through **snapshots** — each commit produces a new snapshot referencing a set of data and delete files via manifest lists/manifests, which is what enables consistent reads and **time travel**. Writers use **optimistic concurrency control**, retrying commits if the base snapshot has moved. Two design choices set Iceberg apart from a plain folder of Parquet files: **hidden partitioning** (partitioning is metadata-driven, e.g. `day(ts)`, not baked into folder paths) and field-ID-based **schema evolution**, both of which allow **partition evolution** and schema changes without rewriting historical data. Deletes are handled via **equality** and **positional delete files** rather than rewriting whole data files, and ongoing **table maintenance** — compaction, manifest rewriting, snapshot expiration, orphan file removal — keeps metadata and the small-files problem under control. A **catalog** (Hive metastore, REST catalog, AWS Glue, etc.) tracks where each table's metadata lives.

## Interview Questions

<QuestionList topic="Iceberg" storagePrefix="iceberg">

<QuestionCard id="iceberg-01" number={1} question="What is Apache Iceberg?" difficulty="easy" topic="Fundamentals">
Apache Iceberg is an open table format for large analytics datasets. It defines how table metadata, snapshots, and data files are managed so multiple engines can read and write the same tables safely. Iceberg tables are usually stored on object storage (S3/GCS/ADLS) with files like Parquet, but the table semantics — transactions, schema/partition evolution — come from Iceberg's own metadata layer.
</QuestionCard>

<QuestionCard id="iceberg-02" number={2} question="What problems does Iceberg solve compared to plain Parquet datasets?" difficulty="medium" topic="Fundamentals">
A plain Parquet "dataset in folders" lacks transactional guarantees and consistent metadata. Iceberg adds ACID-like commits, consistent snapshots, reliable schema/partition evolution, and query planning features like partition pruning based on metadata. It also supports deletes and updates in a table-like way, rather than requiring you to rewrite everything.
</QuestionCard>

<QuestionCard id="iceberg-03" number={3} question="What is a snapshot in Iceberg?" difficulty="medium" topic="Snapshots">
A snapshot is a point-in-time view of the table. Each commit creates a new snapshot that references a set of data and delete files through metadata (manifest lists/manifests). Readers can query a specific snapshot to get consistent results even while writers continue to append or modify the table.
</QuestionCard>

<QuestionCard id="iceberg-04" number={4} question="What is time travel and why is it useful?" difficulty="medium" topic="Time Travel">
Time travel means querying the table "as of" a previous snapshot (or timestamp). It's useful for debugging regressions, auditing changes, reproducing past reports, and safe backfills — computing against a stable snapshot and then committing a new one.
</QuestionCard>

<QuestionCard id="iceberg-05" number={5} question="How does Iceberg handle concurrent writes?" difficulty="hard" topic="Concurrency">
Iceberg typically uses optimistic concurrency control. Writers create new metadata based on a known current snapshot and then attempt to commit; if the base snapshot changed in the meantime, the commit may conflict and must be retried. This prevents silent lost updates and keeps commits atomic.
</QuestionCard>

<QuestionCard id="iceberg-06" number={6} question="What is hidden partitioning in Iceberg?" difficulty="medium" topic="Partitioning">
Hidden partitioning means partitioning is defined at the table metadata level (for example `day(ts)`), not as user-managed folder paths. Engines can still prune partitions, but you're not tied to a physical directory layout. This makes partition evolution safer and avoids leaking storage details into query logic.
</QuestionCard>

<QuestionCard id="iceberg-07" number={7} question="What is partition evolution and why is it important?" difficulty="medium" topic="Partitioning">
Partition evolution allows changing the partition spec over time — for example switching from `day(ts)` to `month(ts)`, or adding a new partition field — without rewriting all historical data. It matters because real datasets change: query patterns evolve, and the "right" partitioning today may not be right in a year.
</QuestionCard>

<QuestionCard id="iceberg-08" number={8} question="How does schema evolution work in Iceberg?" difficulty="medium" topic="Schema">
Iceberg tracks columns by unique field IDs, enabling safe add/drop/rename operations without breaking readers. Schema evolution can be applied while keeping historical snapshots queryable. Some changes, like certain type changes, depend on engine support and can still be risky if consumers assume a fixed schema.
</QuestionCard>

<QuestionCard id="iceberg-09" number={9} question="What are equality deletes and positional deletes?" difficulty="hard" topic="Deletes">
Deletes in Iceberg can be represented as separate delete files:

- **Equality deletes** — delete rows matching a key predicate (for example `id = 123`).
- **Positional deletes** — delete specific row positions in data files.

They allow deletes without rewriting full data files, but too many delete files can hurt read performance until they're compacted.
</QuestionCard>

<QuestionCard id="iceberg-10" number={10} question="How do upserts/merges work with Iceberg?" difficulty="hard" topic="DML">
Upserts are usually implemented by engines (Spark, Flink, Trino) using `MERGE INTO` semantics, which may create new data files and delete files. The exact behavior depends on the engine and write mode. Operationally, merges are often followed by maintenance jobs to compact data files and remove old snapshots.
</QuestionCard>

<QuestionCard id="iceberg-11" number={11} question="Why does the small files problem happen, and how do you mitigate it?" difficulty="medium" topic="Maintenance">
Small files appear when many writers write tiny batches, or when streaming jobs checkpoint frequently. Too many files increase planning overhead and reduce scan efficiency. Mitigations include setting target file sizes, batching writes, and running compaction/rewrite jobs to merge files.
</QuestionCard>

<QuestionCard id="iceberg-12" number={12} question="What maintenance operations are common for Iceberg tables?" difficulty="medium" topic="Maintenance">
Common maintenance includes:

- Rewriting data files (compaction) to hit target file sizes.
- Rewriting manifests to reduce metadata overhead.
- Expiring old snapshots to control metadata growth.
- Removing orphan files.

These jobs keep query planning fast and storage cost under control.
</QuestionCard>

<QuestionCard id="iceberg-13" number={13} question="What is an Iceberg catalog, and what options exist?" difficulty="medium" topic="Catalogs">
A catalog stores table metadata pointers and namespace information. Common options include the Hive metastore, a REST catalog, and cloud-native catalogs (for example AWS Glue). Catalog choice affects authorization, interoperability across engines, and operational complexity.
</QuestionCard>

<QuestionCard id="iceberg-14" number={14} question="How would you migrate an existing dataset to Iceberg?" difficulty="hard" topic="Migration">
You typically create an Iceberg table schema and then either:

- Register existing files in place (where supported), if they already conform to the expected layout.
- Rewrite the data into Iceberg using an engine (Spark/Flink) for safety.

After migration, validate row counts, key constraints, and query performance, then switch readers over to the new table.
</QuestionCard>

<QuestionCard id="iceberg-15" number={15} question="Iceberg vs. Delta vs. Hudi: when would you choose Iceberg?" difficulty="hard" topic="Comparison">
Iceberg is a strong choice when you need an open, engine-agnostic table format with robust metadata, time travel, and evolution features. It fits well in environments with multiple query engines (Spark + Trino + Flink) and a preference for open standards. The best choice still depends on your stack, operational tooling, and update/CDC requirements.
</QuestionCard>

</QuestionList>

## Advanced Iceberg Features

Beyond the basics — the mechanics that show up once a team runs Iceberg at real production scale.

<QuestionList topic="Advanced Features" storagePrefix="iceberg-advanced">

<QuestionCard id="iceberg-16" number={16} question="What is copy-on-write vs. merge-on-read for updates/deletes in Iceberg, and how do you choose?" difficulty="hard" topic="DML">
**Copy-on-write** rewrites entire affected data files immediately when a row changes — reads stay simple and fast (no delete files to reconcile), but writes are expensive, especially for small updates touching large files. **Merge-on-read** just writes a small delete file referencing the changed rows, deferring the expensive rewrite to a later compaction — writes are cheap, but every read has to reconcile data files against pending deletes until compaction catches up. Choose copy-on-write for read-heavy tables with infrequent updates, merge-on-read for write-heavy tables (frequent upserts, CDC ingestion) where write latency matters more.
</QuestionCard>

<QuestionCard id="iceberg-17" number={17} question="What are branches and tags in Iceberg, and how do they enable the Write-Audit-Publish pattern?" difficulty="hard" topic="Branching">
Branches and tags are named references to specific snapshots — a branch can keep advancing (like a git branch), while a tag pins one snapshot permanently (for a monthly archive, say). **Write-Audit-Publish** uses this directly: write new data to a branch (not the main table), run quality/audit checks against that branch in isolation, and only then fast-forward the main branch to include it — so bad data never becomes visible to readers of the main table in the first place.
</QuestionCard>

<QuestionCard id="iceberg-18" number={18} question="What is sort order in Iceberg, and how does it differ from partitioning?" difficulty="medium" topic="Optimization">
Partitioning determines which **files** a query needs to scan at all (coarse-grained pruning); sort order determines how rows are physically ordered **within** those files, which enables finer-grained skipping via file-level column statistics (min/max per file) — a query filtering on a sorted column can skip whole files whose min/max range excludes the filter, even within a single partition. The two are complementary: partitioning narrows down which files to open, sort order narrows down which of those opened files are worth reading further.
</QuestionCard>

<QuestionCard id="iceberg-19" number={19} question="What are manifest lists and manifests, and how do they form Iceberg's metadata tree?" difficulty="hard" topic="Metadata">
A **manifest** lists a set of data (or delete) files along with per-file statistics (partition values, row counts, column bounds) used for pruning. A **manifest list** is a snapshot's index of which manifests belong to it. The hierarchy — snapshot → manifest list → manifests → data files — is what lets query planning avoid touching actual data files at all for the pruning phase, since everything needed to decide which files matter lives in this metadata tree.
</QuestionCard>

<QuestionCard id="iceberg-20" number={20} question="What are Puffin files, and what do they store?" difficulty="hard" topic="Metadata">
Puffin is a file format for storing additional statistics and indexes that don't fit into the standard manifest structure — most notably, information used for improved planning like column-level distinct-value sketches (for cardinality estimation) or secondary indexes. They're an extension point: additional optimization metadata layered on top of the core snapshot/manifest model rather than a replacement for it.
</QuestionCard>

</QuestionList>

## Catalogs, Governance & Multi-Engine Operations

Where table metadata lives, and how Iceberg behaves when several tools share the same tables.

<QuestionList topic="Catalogs & Multi-Engine" storagePrefix="iceberg-catalog">

<QuestionCard id="iceberg-21" number={21} question="What is the Iceberg REST catalog, and why has it become the preferred option over Hive metastore?" difficulty="medium" topic="Catalogs">
The REST catalog exposes catalog operations (list tables, load metadata, commit changes) over a standard HTTP API instead of requiring every engine to speak a specific protocol like Hive's Thrift interface. This decouples engines from any specific catalog implementation — a REST catalog server can be backed by anything (a database, cloud object storage) behind the scenes — making it simpler to add support in new engines and easier to run as a lightweight, cloud-native service instead of operating a full Hive metastore.
</QuestionCard>

<QuestionCard id="iceberg-22" number={22} question="Can you commit changes across multiple Iceberg tables in a single atomic transaction?" difficulty="hard" topic="Transactions">
Yes — multi-table transactions let several tables' changes commit together atomically (all succeed or none do), useful when a logical unit of work spans more than one table (updating a fact table and a related aggregate table consistently). Support and exact API depend on the catalog and engine in use; it's a newer capability relative to Iceberg's original single-table transaction model, not universally available everywhere yet.
</QuestionCard>

<QuestionCard id="iceberg-23" number={23} question="Does Iceberg support views, and how does that help in multi-engine environments?" difficulty="medium" topic="Views">
Yes — the Iceberg view specification defines views with engine-specific SQL dialect variants stored in the same metadata/catalog system as tables, so a view created in one engine can be resolved and queried correctly by a different engine, rather than each engine needing its own separate, incompatible view definitions. This extends Iceberg's "one shared metadata layer, many engines" model from tables to views as well.
</QuestionCard>

<QuestionCard id="iceberg-24" number={24} question="What's the difference between Iceberg format v1 and v2?" difficulty="hard" topic="Spec Versions">
**V1** supports append-only and copy-on-write style tables without row-level delete files. **V2** adds row-level deletes (both equality and positional delete files), enabling efficient merge-on-read updates and deletes without rewriting entire data files. A table's format version is a property of the table itself, and upgrading is generally one-directional — engines need v2 support to correctly interpret delete files, so mixed-engine environments need to confirm every engine involved actually supports the version in use.
</QuestionCard>

</QuestionList>

## Operational Patterns

Running Iceberg with continuous writers, tuning it for write-heavy workloads, and rewriting tables safely.

<QuestionList topic="Operational Patterns" storagePrefix="iceberg-ops">

<QuestionCard id="iceberg-25" number={25} question="How do streaming writers like Flink handle continuous writes into an Iceberg table?" difficulty="hard" topic="Streaming">
A streaming sink batches incoming records over a checkpoint interval and commits them as a new Iceberg snapshot at each checkpoint, rather than committing per-record (which would create the small-files problem almost immediately). This ties Iceberg's commit granularity to the stream processor's own checkpointing, so a table being fed by Flink typically sees one new snapshot per checkpoint interval, with compaction running separately to consolidate the resulting files over time.
</QuestionCard>

<QuestionCard id="iceberg-26" number={26} question="What Iceberg table properties would you tune for a high-write-volume table?" difficulty="hard" topic="Configuration">
Target file size (`write.target-file-size-bytes`) to control how large compacted files end up, the delete file mode (copy-on-write vs. merge-on-read, per the earlier trade-off) matched to the actual write pattern, commit retry settings for optimistic concurrency conflicts under high concurrent write load, and snapshot expiration frequency/retention so metadata doesn't grow unbounded from a high commit rate. Getting these wrong on a high-volume table is exactly how the small-files and metadata-bloat problems show up in practice.
</QuestionCard>

<QuestionCard id="iceberg-27" number={27} question="How do you safely rewrite an entire Iceberg table (e.g., changing file format or fixing a widespread data issue) without downtime for readers?" difficulty="hard" topic="Migration">
Because readers always query against a specific snapshot, you can write the entire rewritten dataset as new data files and commit it as a new snapshot — existing readers mid-query continue safely against the old snapshot they started with, and new queries simply pick up the new one the moment it's committed. This is the same optimistic-commit mechanism that makes ordinary writes safe, just applied to a full-table rewrite instead of an incremental change — there's no window where the table is partially rewritten from a reader's perspective.
</QuestionCard>

</QuestionList>

## Common Interview Scenarios

- **"You have multiple engines — Spark, Trino, Flink — that all need to read and write the same tables. How do you avoid stepping on each other?"** Discuss Iceberg's catalog-based metadata, snapshot isolation, and optimistic concurrency control, which let independent engines commit safely against the same table.
- **"A partitioning scheme chosen a year ago no longer matches query patterns — what are your options?"** Walk through partition evolution: changing the partition spec going forward without rewriting historical data, thanks to hidden partitioning decoupling logical partitions from physical layout.
- **"Query planning on an Iceberg table has gotten slow over time — what would you check?"** Talk through snapshot/manifest bloat from frequent small commits, too many delete files from upserts, and the maintenance jobs (compaction, manifest rewrite, snapshot expiration) that address each.
- **"You need to run data quality checks on new data before it's visible to any downstream reader."** This is the Write-Audit-Publish pattern — write to a branch, audit it in isolation, then fast-forward the main branch only once it passes, so bad data is never visible on the table readers actually query.
- **"A high-volume streaming job keeps writing tiny files into an Iceberg table, and query planning is getting slower every week."** Talk through checkpoint-driven commit granularity from the streaming writer, target file size configuration, and running compaction on a schedule rather than only reactively once planning is already painful.
