## Language Fundamentals in Practice

Why Python shows up everywhere in data platforms, and how its concurrency model plays out in real pipelines.

<QuestionList topic="Language Fundamentals in Practice" storagePrefix="py-prac-fundamentals">

<QuestionCard
  id="py-prac-01"
  number={41}
  question="Why is Python widely used in data engineering?"
  difficulty="easy"
  topic="Fundamentals"
>
Python is popular because it's productive, readable, and has a strong ecosystem for data processing, orchestration, and integration.

- **Glue code** — connecting APIs, databases, and file systems with minimal boilerplate
- **Rich libraries** — pandas, PyArrow, SQLAlchemy, boto3 cover most pipeline needs out of the box
- **Orchestration native** — Airflow, Dagster, and Prefect are all Python-first
- **Interop layer** — even when heavy compute runs on Spark or a warehouse engine, Python is the language stitching the pipeline together

It's rarely the fastest language for raw compute, but it's usually the fastest to build and maintain a correct pipeline in.
</QuestionCard>

<QuestionCard
  id="py-prac-02"
  number={42}
  question="How do iterators and generators help with large data processing?"
  difficulty="medium"
  topic="Fundamentals"
>
Iterators and generators let you stream data instead of loading everything into memory — processing row-by-row or batch-by-batch keeps memory flat regardless of input size.

```python
def batched(iterable, size):
    """Yield successive chunks without materializing the full list."""
    batch = []
    for item in iterable:
        batch.append(item)
        if len(batch) == size:
            yield batch
            batch = []
    if batch:
        yield batch

def process_events(event_stream):
    for chunk in batched(event_stream, size=500):
        write_to_sink(chunk)  # one bounded batch at a time
```

This pattern — pull, don't load — is what lets a single job process files far larger than available RAM.
</QuestionCard>

<QuestionCard
  id="py-prac-03"
  number={43}
  question="What is the difference between threads, multiprocessing, and async IO in Python?"
  difficulty="medium"
  topic="Concurrency"
>
| Approach | Good for | Limited by |
|----------|----------|-----------|
| `threading` | I/O-bound work (network, disk) | GIL — no CPU parallelism |
| `multiprocessing` | CPU-bound work (parsing, transforms) | Process spawn/IPC overhead |
| `asyncio` | Many concurrent I/O waits (API calls) | Single-threaded event loop |

**Rule of thumb:** if the job spends most of its time *waiting* (network, disk), reach for threads or `asyncio`. If it spends its time *computing*, reach for `multiprocessing` or push the work to a native/distributed engine.
</QuestionCard>

<QuestionCard
  id="py-prac-04"
  number={44}
  question="What is the GIL and why does it matter for a data pipeline you're building?"
  difficulty="medium"
  topic="Concurrency"
>
The **Global Interpreter Lock** allows only one thread to execute Python bytecode at a time in CPython, even on a multi-core machine.

In practice, most data engineering jobs are I/O-bound (waiting on S3, a database, or an API), so the GIL rarely matters — threads still help because the GIL is released during I/O. It only becomes a bottleneck when a job is CPU-bound (row-by-row transforms in pure Python), at which point `multiprocessing` or vectorized libraries (pandas/NumPy, which release the GIL in their C internals) are the fix.
</QuestionCard>

</QuestionList>

## Working with Data at Scale

Practical patterns for reading, writing, and moving data reliably in production pipelines.

<QuestionCard

  number={45}
  question="How do you read and write Parquet efficiently in Python?"
  difficulty="medium"
  topic="File Formats"
>
`pyarrow` is the standard choice — it supports columnar reads, predicate pushdown, and explicit schema control.

```python
import pyarrow.parquet as pq

# Read only the columns you need, filtered at the file level
table = pq.read_table(
    "s3://bucket/events/",
    columns=["user_id", "event_type", "ts"],
    filters=[("ts", ">=", "2024-01-01")],
)
```

Guidelines: select only needed columns, keep row groups/files at a reasonable size (avoid the "many tiny files" problem), and hand large datasets off to a distributed engine rather than processing them purely locally.
</QuestionCard>

<QuestionCard
  id="py-prac-06"
  number={46}
  question="How do you process a large CSV file without running out of memory?"
  difficulty="medium"
  topic="File Formats"
>
Stream the file in chunks instead of loading it whole:

```python
import pandas as pd

total = 0
for chunk in pd.read_csv("huge_file.csv", chunksize=100_000):
    total += chunk["amount"].sum()
    chunk.to_parquet(f"out/part-{chunk.index[0]}.parquet")
```

Skip columns you don't need with `usecols`, and prefer writing results incrementally over accumulating them in memory. For anything beyond a few GB, converting to Parquet or moving to distributed processing is usually the better call than tuning chunk size further.
</QuestionCard>

<QuestionCard
  id="py-prac-07"
  number={47}
  question="How do you implement retries with exponential backoff?"
  difficulty="medium"
  topic="Reliability"
>
```python
import random, time, functools

def retry_with_backoff(max_attempts=5, base_delay=0.5):
    def decorator(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            for attempt in range(1, max_attempts + 1):
                try:
                    return fn(*args, **kwargs)
                except TransientError:
                    if attempt == max_attempts:
                        raise
                    delay = base_delay * (2 ** (attempt - 1))
                    time.sleep(delay + random.uniform(0, delay * 0.1))  # jitter
        return wrapper
    return decorator
```

Only retry **transient** errors (timeouts, rate limits) — never retry a schema mismatch or a validation failure. Cap total retry time, and make the operation idempotent so a retried write can't duplicate data.
</QuestionCard>

my_pipeline/

<QuestionCard
  id="py-prac-10"
  number={50}
  question="How do you manage dependencies and reproducible environments?"
  difficulty="easy"
  topic="Project Structure"
>
Pin dependencies with a lockfile (`poetry.lock`, `uv.lock`, or `requirements.txt` with hashes), and isolate environments per project with a virtualenv or container.

Reproducibility also means pinning the Python version itself and building deterministic images — CI should build and test against the exact same environment definition that runs in production, not a looser "close enough" one.

<QuestionCard
  id="py-prac-11"
  number={51}
  question="How do you test data transformations in Python?"
  difficulty="medium"
  topic="Testing"

```python
def test_normalize_revenue_golden_case():
    input_df = pd.DataFrame({"id": [1], "revenue_cents": [1050]})

    assert result["revenue"].iloc[0] == 10.50

@given(revenue_cents=st.integers(min_value=0))

```

Combine small **golden-case** fixtures (known input → known output) with **property-based tests** (`hypothesis`) for invariants that must hold across all inputs, like non-negative amounts or no duplicate keys. <QuestionCard
  id="py-prac-12"
  number={52}
  question="How do you profile and optimize slow Python code?"
  difficulty="hard"
  topic="Performance"
>
Profile before optimizing — guessing at bottlenecks wastes time:

```python
import cProfile
cProfile.run("process_data(df)", sort="cumulative")
```

Common fixes, in order of how often they apply:
1. **Vectorize** — replace `iterrows()`/Python loops with pandas/NumPy operations
2. **Reduce copies** — avoid chained `.loc`/`.copy()` calls that duplicate large frames
3. **Offload CPU work** — `multiprocessing`, or push to a native/distributed engine
4. **Cache repeated I/O** — `functools.lru_cache`, or batch reads instead of per-row calls

`py-spy` is worth knowing for production debugging — it's a sampling profiler that attaches to a running process with effectively zero overhead.
</QuestionCard>

</QuestionList>

def fetch_all_pages(client, endpoint):

    while url:

<QuestionCard

  question="How do you manage configuration and secrets across environments in a Python pipeline?"

import os
from dataclasses import dataclass

@dataclass
class Settings:
    db_url: str
    batch_size: int = 1000

def load_settings() -> Settings:

        db_url=os.environ["DB_URL"],              # required — fail fast if missing

Read configuration from environment variables (or a secrets manager for credentials), never hardcode secrets in source, and fail immediately at startup if a required value is missing rather than failing confusingly mid-run.   difficulty="hard"
  topic="Connections"
>
```python
from sqlalchemy import create_engine

engine = create_engine(
    "postgresql://...",
    pool_size=10,        # keep this many connections warm

    pool_pre_ping=True,   # check a connection is alive before handing it out
)
```

Create the engine/pool **once** at process startup, not per request or per row — recreating connections per operation is a common source of both poor performance and eventually exhausting the database's connection limit. `pool_pre_ping` protects against handing out a connection that's silently gone stale (common after idle periods or a database failover).

## Serialization & Data Formats in Practice

Handling the messy realities of real-world ingested data — mixed formats, encodings, and partial failures.

<QuestionList topic="Serialization & Data Formats in Practice" storagePrefix="py-prac-fmt">

<QuestionCard
  id="py-prac-fmt-01"
  number={58}
  question="How do you choose between JSON, Avro, and Protobuf for a data pipeline?"
  difficulty="medium"
  topic="Serialization"
>
**JSON** — human-readable, no schema enforcement, widest tooling support; good for APIs and low-volume/debugging-friendly paths. **Avro** — compact binary format with an embedded schema, strong support for schema evolution, common in Kafka pipelines. **Protobuf** — compact binary, schema defined separately and compiled, very fast, common for service-to-service RPC (gRPC).

In practice: JSON when human-readability and flexibility matter more than size/speed, Avro when you need schema evolution inside a streaming pipeline, Protobuf when you need a fast, strongly-typed contract between services.
</QuestionCard>

<QuestionCard
  id="py-prac-fmt-02"
  number={59}
  question="How do you handle inconsistent date formats coming from multiple upstream sources?"
  difficulty="medium"
  topic="Datetime"

```python
from dateutil import parser

def parse_flexible_date(value: str):
    try:
        return parser.parse(value)   # handles many formats automatically
    except (ValueError, TypeError):
        logger.warning("Unparseable date: %r", value)

```

`dateutil.parser` handles a wide range of formats without per-source format strings, but for high-volume pipelines it's worth maintaining an explicit per-source format map (faster, and fails loudly instead of guessing) rather than relying on flexible parsing everywhere. Either way, always normalize to UTC immediately after parsing.

<QuestionCard
  id="py-prac-fmt-03"
  number={60}
  question="How do you detect and handle character encoding issues in ingested files?"
  difficulty="hard"

import chardet

with open("upstream_export.csv", "rb") as f:

<QuestionCard
  id="py-prac-fmt-04"
  number={61}
  question="How would you deduplicate records in a stream using a rolling window in Python?"
  difficulty="hard"
  topic="Streaming"
>
```python
from collections import deque

class RollingDeduplicator:
    def __init__(self, window_size=10_000):
        self.seen = set()
        self.order = deque(maxlen=window_size)

    def is_duplicate(self, record_id: str) -> bool:
        if record_id in self.seen:
            return True
        if len(self.order) == self.order.maxlen:
            oldest = self.order[0]
            self.seen.discard(oldest)   # evict the oldest id as the window slides
        self.order.append(record_id)
        self.seen.add(record_id)
        return False
```

A `deque` with `maxlen` combined with a `set` gives O(1) membership checks with a bounded memory footprint — the set alone would grow unbounded over an infinite stream, so the deque enforces a sliding window of "recently seen" ids that age out automatically.
</QuestionCard>

<QuestionCard
  id="py-prac-fmt-05"
  number={62}
  question="How do you safely handle partially-written or corrupted files during ingestion?"
  difficulty="medium"
  topic="Reliability"
>
```python
import os

def atomic_write(path, data):
    tmp_path = f"{path}.tmp"
    with open(tmp_path, "wb") as f:
        f.write(data)
    os.replace(tmp_path, path)   # atomic on the same filesystem — no partial file visible
```

On the **write** side, write to a temp path and atomically rename it into place, so a consumer never sees a half-written file. On the **read** side, validate what you read (checksum, expected row count, schema check) before treating it as good, and quarantine or reject files that fail validation rather than silently processing a truncated file as if it were complete.
</QuestionCard>

## Modern Python in Pipelines

Applying type hints, dataclasses, and pattern matching to real pipeline code, not just toy examples.

<QuestionCard
  id="py-prac-modern-01"
  number={63}
  question="How would you use a dataclass to define a pipeline's configuration?"
  difficulty="easy"
  topic="Dataclasses"
>
```python
from dataclasses import dataclass, field

@dataclass
class IngestConfig:
    source_bucket: str
    table_name: str
    columns: list[str] = field(default_factory=list)   # mutable defaults need field()
    batch_size: int = 5000
```

A dataclass gives the config attribute access and a generated `__repr__` (so logging the config for a run is readable), catches typos as attribute errors instead of silent `KeyError`s from a dict, and — combined with type hints — lets a type checker catch a caller passing the wrong type before the job ever runs.
</QuestionCard>

def load_partition(table: str, run_date: str, retries: int = 3) -> int:

<QuestionCard
  id="py-prac-modern-03"
  number={65}
  question="How would you use match/case to route records by event type in an ingestion job?"
  difficulty="medium"
  topic="Pattern Matching"
>
```python
def handle_event(event: dict):
    match event:
        case {"type": "user_created", "user_id": uid}:
            upsert_user(uid, event)
        case {"type": "user_deleted", "user_id": uid}:
            soft_delete_user(uid)
        case {"type": str(unknown_type)}:
            logger.warning("Unhandled event type: %s", unknown_type)
        case _:
            logger.error("Malformed event, missing type: %r", event)
```

This reads as a clear dispatch table for the shapes you expect, and — unlike a chain of `if "type" in event and event["type"] == ...` checks — naturally falls through to an explicit "unknown/malformed" branch, so unexpected event shapes are handled deliberately instead of silently ignored.
</QuestionCard>

<QuestionCard
  id="py-prac-modern-04"
  number={66}
  question="How do you use functools.lru_cache safely in a long-running pipeline process?"
  difficulty="hard"
  topic="Performance"
>
```python
from functools import lru_cache

@lru_cache(maxsize=10_000)
def lookup_country_name(country_code: str) -> str:
    return reference_data_client.get_country(country_code)   # expensive I/O call
```

Safe uses are for **pure, small-cardinality lookups** — reference/dimension data that rarely changes and has a bounded number of distinct inputs. It's unsafe (or at least suspicious) to cache anything based on mutable external state without a `maxsize` (unbounded growth = slow memory leak in a long-running process) or anything that needs to reflect updates during the process's lifetime, since `lru_cache` has no built-in expiry.
</QuestionCard>

<QuestionCard
  id="py-prac-modern-05"
  number={67}
  question="How would you use itertools to batch an unbounded stream of records for writing?"
  difficulty="medium"
  topic="Itertools"
>
```python
from itertools import islice

def batched(iterable, size):
    it = iter(iterable)
    while batch := list(islice(it, size)):
        yield batch

for batch in batched(read_kafka_stream(), size=500):
    write_to_sink(batch)
```

`islice` pulls a bounded chunk off a shared iterator without knowing or caring how long the overall stream is — combined with the walrus operator to stop cleanly when a batch comes back empty, this pattern batches a genuinely unbounded stream (a Kafka consumer, a paginated API) using constant memory, regardless of total volume.
</QuestionCard>

</QuestionList>
