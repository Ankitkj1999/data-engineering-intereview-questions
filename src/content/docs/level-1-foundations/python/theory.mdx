<QuestionCard
  id="py-fund-02"
  number={2}
  question="What is the difference between a mutable and an immutable object? Give examples of each."
  difficulty="easy"
  topic="Fundamentals"
>
**Mutable** objects can be changed after creation:
- `list` — `my_list.append(4)` modifies in place
- `dict` — `my_dict["key"] = "value"` modifies in place
- `set` — `my_set.add(5)` modifies in place

**Immutable** objects cannot be changed:
- `int`, `float`, `bool` — reassignment creates a new object
- `str` — `"hello" + "!"` returns a new string
- `tuple` — elements cannot be added, removed, or changed
- `frozenset` — immutable version of set

**Why it matters for data engineering:** immutable objects are safe as dict keys or set members; sharing mutable objects across threads causes subtle bugs.
</QuestionCard>

<QuestionCard
  id="py-fund-03"
  number={3}
  question="Explain the difference between == and is in Python."
  difficulty="easy"
  topic="Fundamentals"
>
| Operator | Checks | Example |
|----------|--------|---------|
| `==` | **Value equality** — same value? | `[1,2] == [1,2]` → `True` |
| `is` | **Identity** — same object in memory? | `[1,2] is [1,2]` → `False` |

```python
a = [1, 2, 3]
b = a           # same reference
c = [1, 2, 3]   # new object, same value

print(a == c)   # True  — same value
print(a is b)   # True  — same object
print(a is c)   # False — different objects
```

> Use `is` only for singleton checks (`if x is None`). Use `==` for all value comparisons.
</QuestionCard>

<QuestionCard
  id="py-fund-04"
  number={4}
  question="How does memory management and garbage collection work in Python?"
  difficulty="medium"
  topic="Fundamentals"
>
Python uses two mechanisms:

**1. Reference Counting**
Every object tracks how many references point to it. When the count hits 0 the memory is freed immediately.

```python
import sys
a = [1, 2, 3]
print(sys.getrefcount(a))  # 2 (a + getrefcount arg itself)
del a  # refcount → 0, memory freed
```

**2. Cyclic Garbage Collector**
Reference counting cannot handle circular references (A → B → A). Python's `gc` module runs periodically to detect and clean these cycles.

```python
import gc
gc.collect()  # manually trigger GC
```

**Memory pools:** CPython uses `pymalloc`, a private heap for small objects (≤ 512 bytes), reducing `malloc` overhead.

**For data engineering:** use `del df` + `gc.collect()` after processing large DataFrames, or prefer chunked processing to avoid OOM.
</QuestionCard>

<QuestionCard
  id="py-fund-05"
  number={5}
  question="What is the Global Interpreter Lock (GIL) and how does it affect data engineering workloads?"
  difficulty="hard"
  topic="Concurrency"
>
The **GIL** is a mutex in CPython that allows only one thread to execute Python bytecode at a time, even on multi-core machines.

**Impact by workload type:**

| Workload | GIL Impact | Solution |
|----------|-----------|---------|
| I/O-bound (network, disk) | Minimal — GIL released during I/O | `threading` or `asyncio` |
| CPU-bound (parsing, transforms) | Full — only one core used | `multiprocessing` |
| NumPy / pandas ops | Minimal — C extensions release GIL | Can use threads |

```python
from multiprocessing import Pool

def process_partition(chunk):
    return chunk.apply(some_transform)

with Pool(processes=4) as pool:
    results = pool.map(process_partition, chunks)
```

> Python 3.13 introduced an experimental **no-GIL** build (PEP 703). This will change concurrent Python data pipeline design.
</QuestionCard>

</QuestionList>

## Functions & Generators

Essential Python patterns for building efficient, composable data pipelines.

<QuestionList topic="Functions & Generators" storagePrefix="py-functions">

<QuestionCard
  id="py-fn-01"
  number={6}
  question="What are generators and why are they useful in data engineering?"
  difficulty="medium"
  topic="Generators"
>
A **generator** uses `yield` instead of `return` — it produces values lazily, one at a time, without loading everything into memory.

```python
# ❌ Loads all 1M rows into memory at once
def read_all_rows(file):
    rows = []
    with open(file) as f:
        for line in f:
            rows.append(line)
    return rows

# ✅ Yields one row at a time — memory stays flat
def stream_rows(file):
    with open(file) as f:
        for line in f:
            yield line.strip()

for row in stream_rows("huge_file.csv"):
    process(row)
```

**Why critical for data engineering:**
- Process multi-GB files without OOM errors
- Build composable, lazy pipeline stages
- Power `chunksize` patterns in pandas

**Generator expression** (inline):
```python
total = sum(len(line) for line in open("file.txt"))
```
</QuestionCard>

<QuestionCard
  id="py-fn-02"
  number={7}
  question="Explain *args and **kwargs. When would you use them in data pipelines?"
  difficulty="easy"
  topic="Functions"
>
- **`*args`** — captures extra positional arguments as a **tuple**
- **`**kwargs`** — captures extra keyword arguments as a **dict**

```python
def log_event(event_type, *args, **kwargs):
    print(f"Event: {event_type}")
    print(f"Values: {args}")
    print(f"Metadata: {kwargs}")

log_event("click", 100, 200, user_id=42, session="abc")
# Event: click
# Values: (100, 200)
# Metadata: {'user_id': 42, 'session': 'abc'}
```

**Data engineering use case — flexible reader wrapper:**
```python
def read_data(path, *args, **kwargs):
    """Forward extra options to the right pandas reader."""
    if path.endswith(".parquet"):
        return pd.read_parquet(path, **kwargs)
    return pd.read_csv(path, *args, **kwargs)
```
</QuestionCard>

<QuestionCard
  id="py-fn-03"
  number={8}
  question="What are decorators and how would you use one in a data pipeline?"
  difficulty="medium"
  topic="Functions"
>
A **decorator** wraps a function to extend its behaviour without modifying it directly.

```python
import time, functools

def timer(func):
    @functools.wraps(func)  # preserves __name__ and docstring
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.perf_counter() - start:.3f}s")
        return result
    return wrapper

@timer
def load_dataset(path):
    import pandas as pd
    return pd.read_parquet(path)

df = load_dataset("sales.parquet")
# load_dataset took 0.243s
```

**Common DE decorator patterns:**
- `@retry(max_attempts=3)` — resilient API / DB calls
- `@log_inputs` — audit trail for transformations
- `@validate_schema` — assert DataFrame shape before writing

Airflow, dbt, and Prefect all use decorators (`@dag`, `@task`) to register pipeline units.
</QuestionCard>

OOP patterns used in data engineering frameworks and libraries.

<QuestionCard
  id="py-oop-01"
  number={9}
  question="What is the difference between class methods, static methods, and instance methods?"
  difficulty="medium"
  topic="OOP"
>
| Method type | Decorator | First arg | Can access |
|-------------|-----------|-----------|------------|
| Instance | *(none)* | `self` | instance + class |
| Class | `@classmethod` | `cls` | class only |
| Static | `@staticmethod` | *(none)* | neither |

```python
class DatabaseConnector:
    _default_port = 5432

    def __init__(self, host, port=None):
        self.host = host
        self.port = port or self._default_port

    def connect(self):
        # Instance method — uses self
        return f"Connecting to {self.host}:{self.port}"

    @classmethod
    def from_url(cls, url: str):
        # Class method — factory pattern
        host, port = url.split(":")
        return cls(host, int(port))

    @staticmethod
    def validate_port(port: int) -> bool:
        # Static — pure utility, no state needed
        return 1 <= port <= 65535

db = DatabaseConnector.from_url("localhost:5432")
print(DatabaseConnector.validate_port(5432))  # True
```
</QuestionCard>

<QuestionCard
  id="py-oop-02"
  number={10}
  question="What are Python's magic (dunder) methods? Give examples relevant to data engineering."
  difficulty="medium"
  topic="OOP"
>
**Magic methods** (dunder = double underscore) let you define how objects behave with built-in operators and functions.

```python
class DataPipeline:
    def __init__(self, steps: list):
        self.steps = steps

    def __repr__(self):
        return f"DataPipeline(steps={self.steps})"

    def __len__(self):
        # len(pipeline)
        return len(self.steps)

    def __iter__(self):
        # for step in pipeline
        return iter(self.steps)

    def __add__(self, other):
        # pipeline1 + pipeline2
        return DataPipeline(self.steps + other.steps)

    def __contains__(self, step):
        # "transform" in pipeline
        return step in self.steps

extract = DataPipeline(["extract"])
load    = DataPipeline(["transform", "load"])
full    = extract + load
print(len(full))              # 3
print("transform" in full)    # True
```

**Key dunder methods for DE:**
- `__enter__` / `__exit__` — context manager for resource cleanup
- `__getitem__` — custom indexing on dataset wrappers
- `__call__` — make transformer objects callable like functions
</QuestionCard>

</QuestionList>

## Concurrency & Performance

Threading, async, and profiling patterns for high-throughput pipelines.

<QuestionList topic="Concurrency & Performance" storagePrefix="py-concurrency">

<QuestionCard
  id="py-conc-01"
  number={11}
  question="What is the difference between threading, multiprocessing, and asyncio?"
  difficulty="hard"
  topic="Concurrency"
>
| Approach | Best for | GIL affected? | Overhead |
|----------|----------|--------------|---------|
| `threading` | I/O-bound (HTTP, DB queries) | Yes | Low |
| `multiprocessing` | CPU-bound (data transforms) | No | High (process spawn) |
| `asyncio` | Many concurrent I/O ops | Yes | Very low |

```python
# asyncio — ideal for many concurrent API calls
import asyncio, httpx

async def fetch(url, client):
    r = await client.get(url)
    return r.json()

async def fetch_all(urls):
    async with httpx.AsyncClient() as client:
        return await asyncio.gather(*[fetch(u, client) for u in urls])

results = asyncio.run(fetch_all(["https://api.example.com/data"] * 100))
```

**Rule of thumb for data engineering:**
- Reading 100 S3 files in parallel → `asyncio` or `ThreadPoolExecutor`
- Transforming 10 million rows → `multiprocessing.Pool`
- Single background task → `threading.Thread`
</QuestionCard>

<QuestionCard
  id="py-conc-02"
  number={12}
  question="How do you profile and optimize a slow Python data pipeline?"
  difficulty="hard"
  topic="Performance"
>
**Step 1 — Profile first, optimize second:**
```python
import cProfile
cProfile.run('process_data(df)', sort='cumulative')
```

**Step 2 — Common bottlenecks and fixes:**

| Bottleneck | Symptom | Fix |
|------------|---------|-----|
| Python loops over rows | Slow `iterrows()` | Vectorize with pandas / NumPy |
| Repeated I/O | High disk/net read time | Batch reads, cache with `functools.lru_cache` |
| Single-threaded CPU | One core at 100% | `multiprocessing.Pool` |
| Memory pressure | OOM / swap thrashing | Generator / chunked processing |

```python
# ❌ Slow — Python loop
for idx, row in df.iterrows():
    df.at[idx, 'total'] = row['price'] * row['qty']

# ✅ Fast — vectorized
df['total'] = df['price'] * df['qty']
```

**Useful profiling tools:**
- `cProfile` / `snakeviz` — function-level timings
- `memory_profiler` — line-by-line memory usage
- `py-spy` — sampling profiler, zero overhead on production
</QuestionCard>

## Comprehensions & Functional Patterns

Concise, idiomatic ways to transform data without writing explicit loops.

<QuestionList topic="Comprehensions & Functional Patterns" storagePrefix="py-comp">

<QuestionCard
  id="py-comp-01"
  number={15}
  question="What are list, dict, and set comprehensions, and why prefer them over loops?"
  difficulty="easy"
  topic="Comprehensions"
>
Comprehensions build a collection in a single expression instead of an explicit loop with `.append()`/assignment:

```python
squares = [n ** 2 for n in range(10)]                       # list
by_id   = {row["id"]: row for row in records}               # dict
unique  = {row["user_id"] for row in records}                # set
```

They're preferred because they're usually faster (the loop runs in C, not Python bytecode), more concise, and signal intent clearly — "this builds a new collection" — rather than mixing that intent with manual accumulator bookkeeping.
</QuestionCard>

<QuestionCard
  id="py-comp-02"
  number={16}
  question="What's the difference between a list comprehension and a generator expression?"
  difficulty="easy"
  topic="Comprehensions"
>
```python
squares_list = [n ** 2 for n in range(1_000_000)]   # built eagerly, all in memory
squares_gen  = (n ** 2 for n in range(1_000_000))   # lazy, one value at a time
```

The only syntax difference is `[]` vs `()`, but the memory behavior is completely different — a list comprehension materializes the entire result immediately, while a generator expression produces values on demand. Use a generator expression when you're piping the result into something that consumes it once (`sum(...)`, another loop) and don't need it as an indexable collection.
</QuestionCard>

<QuestionCard
  id="py-comp-03"
  number={17}
  question="How do map(), filter(), and functools.reduce() work, and when would you prefer a comprehension instead?"
  difficulty="medium"
  topic="Functional"
>
```python
from functools import reduce

doubled  = map(lambda x: x * 2, values)              # apply a function to each item
positive = filter(lambda x: x > 0, values)           # keep items matching a predicate
total    = reduce(lambda a, b: a + b, values, 0)     # fold into a single value
```

`map`/`filter` return lazy iterators (like generator expressions), and `reduce` collapses an iterable into one accumulated result. In practice, a comprehension is usually preferred over `map`/`filter` for readability (`[x * 2 for x in values if x > 0]` reads more directly than nested calls), but `reduce` still earns its place for genuine folds that don't map cleanly onto a comprehension.
</QuestionCard>

<QuestionCard
  id="py-comp-04"
  number={18}
  question="What is a lambda function and when is it appropriate to use one?"
  difficulty="easy"
  topic="Functional"
>
A `lambda` is a small, anonymous, single-expression function: `lambda x: x * 2` is equivalent to a one-line `def`. They're appropriate for short, throwaway logic passed inline — a `sort` key, a `map`/`filter` callback — but not for anything with multiple statements, a docstring, or logic worth naming and reusing; at that point a regular `def` is clearer and easier to test.

```python
records.sort(key=lambda r: r["created_at"])
```
</QuestionCard>

<QuestionCard
  id="py-comp-05"
  number={19}
  question="What does the walrus operator (:=) do, and where is it useful in a data pipeline?"
  difficulty="medium"
  topic="Functional"
>
`:=` assigns a value and returns it in the same expression, letting you avoid computing something twice:

```python
# Without walrus — the read happens twice, or needs an extra line
while (line := file.readline()):
    process(line)

# Useful inside a comprehension to avoid recomputation
results = [y for x in data if (y := expensive(x)) is not None]
```

It's most useful anywhere you'd otherwise call the same expensive function or I/O call once to check a condition and again to use the value.
</QuestionCard>

## Scope, Closures & Context Managers

How Python resolves names, captures state in nested functions, and manages resource lifecycles.

<QuestionList topic="Scope, Closures & Context Managers" storagePrefix="py-scope">

<QuestionCard
  id="py-scope-01"
  number={20}
  question="What is the LEGB rule for variable scope resolution?"
  difficulty="medium"
  topic="Scope"
>
Python looks up a name in this order: **L**ocal (current function) → **E**nclosing (any outer function it's nested in) → **G**lobal (module level) → **B**uilt-in (`len`, `print`, etc.). The lookup stops at the first scope where the name is found.

```python
x = "global"

def outer():
    x = "enclosing"
    def inner():
        print(x)  # "enclosing" — found in the enclosing scope before global
    inner()

outer()
```
</QuestionCard>

<QuestionCard
  id="py-scope-02"
  number={21}
  question="What is a closure, and how would you use one to build a configurable transformation function?"
  difficulty="medium"
  topic="Scope"
>
A closure is a function that "remembers" variables from its enclosing scope even after that scope has finished executing:

```python
def make_multiplier(factor):
    def multiply(value):
        return value * factor   # factor is captured from the enclosing scope
    return multiply

to_cents = make_multiplier(100)
to_cents(19.99)  # 1999.0
```

This is a common pattern for building a family of small, pre-configured transformation functions (unit converters, column renamers) without writing a full class for each one.
</QuestionCard>

<QuestionCard
  id="py-scope-03"
  number={22}
  question="What does the nonlocal keyword do?"
  difficulty="medium"
  topic="Scope"
>
`nonlocal` lets an inner function **assign** to a variable in its enclosing (not global) scope, rather than creating a new local variable that shadows it:

```python
def make_counter():
    count = 0
    def increment():
        nonlocal count
        count += 1   # without nonlocal, this raises UnboundLocalError
        return count
    return increment

counter = make_counter()
counter()  # 1
counter()  # 2
```
</QuestionCard>

<QuestionCard
  id="py-scope-04"
  number={23}
  question="How do you write a custom context manager, and why would a data pipeline need one?"
  difficulty="medium"
  topic="Context Managers"
>
Define `__enter__` and `__exit__` to guarantee setup/teardown runs even if an exception occurs partway through:

```python
class ManagedConnection:
    def __enter__(self):
        self.conn = create_connection()
        return self.conn

    def __exit__(self, exc_type, exc_val, exc_tb):
        self.conn.close()   # always runs, even on exception
        return False        # don't suppress the exception

with ManagedConnection() as conn:
    conn.execute(query)
```

Pipelines need this anywhere a resource (DB connection, file handle, distributed lock, temp directory) must be released even when the code inside the block fails — without it, a failed transform can leak connections until the process runs out of them.
</QuestionCard>

<QuestionCard
  id="py-scope-05"
  number={24}
  question="What's the difference between contextlib.contextmanager and defining __enter__/__exit__ directly?"
  difficulty="hard"
  topic="Context Managers"
>
`@contextlib.contextmanager` lets you write a context manager as a single generator function instead of a class:

```python
from contextlib import contextmanager

@contextmanager
def managed_connection():
    conn = create_connection()
    try:
        yield conn          # code inside the `with` block runs here
    finally:
        conn.close()        # guaranteed cleanup, like __exit__

with managed_connection() as conn:
    conn.execute(query)
```

It's more concise for simple cases (one resource, no extra methods needed on the object), while a class-based context manager is worth it when the object also needs other methods/state beyond just entering and exiting.
</QuestionCard>

</QuestionList>

## Collections & Itertools

<QuestionCard

  question="When would you use a defaultdict instead of a regular dict?"
  difficulty="easy"
  topic="Collections"

```python
from collections import defaultdict

groups = defaultdict(list)
for row in records:
    groups[row["category"]].append(row)   # no need to check "if key not in groups"
```

Use it whenever you're grouping or accumulating into a dict and would otherwise write `if key not in d: d[key] = ...` before every update — `defaultdict` removes that boilerplate and the risk of forgetting it in one code path.
</QuestionCard>

<QuestionCard
  id="py-coll-03"
  number={27}
  question="What is Counter, and what's a practical data engineering use for it?"
  difficulty="easy"
  topic="Collections"
>
```python
from collections import Counter

event_counts = Counter(row["event_type"] for row in records)
event_counts.most_common(5)   # top 5 event types by frequency
```

`Counter` is a dict subclass for tallying hashable items, with built-in `.most_common()` for ranking. It's a quick way to profile a dataset — value frequency checks, finding the most common error codes in a log, spotting an unexpectedly dominant category before it's worth writing a full aggregation query.
</QuestionCard>

<QuestionCard
  id="py-coll-04"
  number={28}
  question="What's the difference between a list and a deque, and when does it matter for pipeline code?"
  difficulty="medium"
  topic="Collections"
>
A `list` has O(1) appends/pops at the **end** but O(n) at the **start** (every remaining element shifts). A `deque` (double-ended queue) has O(1) at **both** ends.

```python
from collections import deque

recent_events = deque(maxlen=1000)   # fixed-size rolling window, oldest drops automatically
recent_events.append(new_event)
```

It matters for any rolling-window or queue-like pipeline pattern — a sliding window of recent events, a work queue being consumed from the front while new items arrive at the back — where a plain list would silently become a performance problem as it grows.
</QuestionCard>

<QuestionCard
  id="py-coll-05"
  number={29}
  question="What does itertools.groupby() do, and what's the most common mistake when using it?"
  difficulty="hard"
  topic="Itertools"
>
```python
from itertools import groupby

for key, group in groupby(records, key=lambda r: r["category"]):
    print(key, list(group))
```

`groupby` only groups **consecutive** matching items — it does not sort first. The most common mistake is calling it on unsorted data and getting multiple separate groups for the same key instead of one:

```python
data = ["a", "b", "a"]
# without sorting, groupby sees three separate runs: "a", "b", "a" — not one "a" group
sorted_data = sorted(data)
```

Always `sort()` (or ensure the input is already sorted) on the grouping key before calling `groupby`.
</QuestionCard>

from itertools import chain, islice

all_rows = chain(batch1, batch2, batch3)

## Modern Python & Type System

Type hints, dataclasses, and pattern matching — features that make pipeline code safer and more self-documenting.

<QuestionList topic="Modern Python & Type System" storagePrefix="py-modern">

<QuestionCard
  id="py-modern-01"
  number={31}
  question="What are type hints, and do they change Python's runtime behavior?"
  difficulty="easy"
  topic="Type Hints"
>
```python
def normalize(revenue_cents: int) -> float:
    return revenue_cents / 100
```

Type hints are annotations that document expected types — Python itself does **not** enforce them at runtime; the function above still runs even if you pass a string. Their value comes from static type checkers (`mypy`, `pyright`) catching mismatches before deployment, and from making function signatures self-documenting for anyone reading or calling the code.
</QuestionCard>

<QuestionCard
  id="py-modern-02"
  number={32}
  question="How do you use Optional, Union, and generics from the typing module?"
  difficulty="medium"
  topic="Type Hints"
>
```python
from typing import Optional, Union

def find_user(user_id: int) -> Optional[dict]:      # dict, or None
    ...

def parse_amount(value: Union[int, str]) -> float:   # int OR str
    ...

# Python 3.10+ shorthand for both:
def find_user(user_id: int) -> dict | None: ...
def parse_amount(value: int | str) -> float: ...
```

`Optional[X]` is shorthand for `Union[X, None]` — use it whenever a function can legitimately return or accept nothing. Generics (`list[int]`, `dict[str, float]`) go further and describe the type of a collection's contents, not just the collection type itself.
</QuestionCard>

<QuestionCard
  id="py-modern-03"
  number={33}
  question="What is a dataclass, and when would you use one instead of a plain class or a dict?"
  difficulty="medium"
  topic="Dataclasses"
>
```python
from dataclasses import dataclass

@dataclass
class PipelineConfig:
    source_path: str
    batch_size: int = 1000
    dry_run: bool = False

cfg = PipelineConfig(source_path="s3://bucket/data")
```

`@dataclass` auto-generates `__init__`, `__repr__`, and `__eq__` from the annotated fields, removing the boilerplate of writing them by hand. Prefer it over a plain dict when the structure is fixed and known ahead of time (you get attribute access, type hints, and IDE autocomplete instead of stringly-typed keys), and over a hand-written class when you don't need custom behavior beyond holding data.
</QuestionCard>

<QuestionCard
  id="py-modern-04"
  number={34}
  question="What is structural pattern matching (match/case), and when is it clearer than if/elif?"
  difficulty="medium"
  topic="Pattern Matching"
>
```python
match event:
    case {"type": "insert", "table": table, "data": data}:
        handle_insert(table, data)
    case {"type": "delete", "table": table, "id": row_id}:
        handle_delete(table, row_id)
    case _:
        raise ValueError(f"Unknown event shape: {event}")
```

Introduced in Python 3.10, `match`/`case` can destructure a value's **shape** (dict keys, list length, object attributes) as part of the match, not just compare it — which makes it clearer than `if/elif` chains for routing logic based on a record's structure, like dispatching different event or message shapes in an ingestion pipeline.
</QuestionCard>

<QuestionCard
  id="py-modern-05"
  number={35}
  question="What is a Protocol in the typing module, and how does it enable structural typing?"
  difficulty="hard"
  topic="Type Hints"
>
```python
from typing import Protocol

class Writable(Protocol):
    def write(self, data: bytes) -> int: ...

def save(destination: Writable, data: bytes):
    destination.write(data)
```

A `Protocol` describes a **shape** (what methods/attributes an object must have) rather than a specific class hierarchy — any object with a matching `write` method satisfies `Writable`, whether or not it inherits from anything in particular. This is Python's version of "duck typing, but checkable" — useful for accepting a file handle, an S3 client wrapper, or an in-memory buffer interchangeably, as long as each implements the same interface.
</QuestionCard>

<QuestionCard
  id="py-modern-06"
  number={36}
  question="What's the difference between typing.TypedDict and a dataclass for representing structured records?"
  difficulty="hard"
  topic="Type Hints"
>
```python
from typing import TypedDict
from dataclasses import dataclass

class UserRecord(TypedDict):
    id: int
    name: str

@dataclass
class UserRecord:
    id: int
    name: str
```

`TypedDict` type-checks a **plain dict** — the record is still a real `dict` at runtime (useful when working with JSON payloads that are naturally dict-shaped, like API responses). A `dataclass` creates an actual **object** with attribute access (`user.name` instead of `user["name"]`) and generated `__init__`/`__repr__`/`__eq__`. Use `TypedDict` when interoperating with dict-based APIs; use a dataclass when you want a first-class object with behavior.
</QuestionCard>

## Data Serialization & Parsing

Handling dates, encodings, structured formats, and the numeric precision issues that trip up ingestion pipelines.

<QuestionList topic="Data Serialization & Parsing" storagePrefix="py-parse">

<QuestionCard
  id="py-parse-01"
  number={37}
  question="How do you work with dates, times, and timezones correctly in Python?"
  difficulty="medium"
  topic="Datetime"
>
```python
from datetime import datetime, timezone

# Always store and compare in UTC — convert to local time only for display
now_utc = datetime.now(timezone.utc)

# Naive datetimes (no tzinfo) are a common source of silent bugs —
# comparing a naive and an aware datetime raises TypeError
naive = datetime(2024, 1, 1)          # no timezone attached — ambiguous
aware = datetime(2024, 1, 1, tzinfo=timezone.utc)
```

The core rule for pipelines: make every datetime **timezone-aware** as early as possible on ingestion, store everything in UTC, and only convert to a local timezone at the point of display — mixing naive and aware datetimes is one of the most common sources of off-by-some-hours bugs in production pipelines.
</QuestionCard>

<QuestionCard
  id="py-parse-02"
  number={38}
  question="What's the difference between json.dumps/loads and pickle, and when is pickle unsafe to use?"
  difficulty="medium"
  topic="Serialization"
>
`json` serializes to a human-readable, language-agnostic text format, but only supports a limited set of types (no dates, sets, or custom objects without extra work). `pickle` serializes almost any Python object, including custom classes, but produces Python-specific binary output that other languages can't read.

**Security warning:** `pickle.loads()` on data from an untrusted source is unsafe — unpickling can execute arbitrary code embedded in the byte stream. Only unpickle data you produced yourself or fully trust; for data crossing a trust boundary (an API, a queue, another team's system), use JSON or a schema-validated format instead.
</QuestionCard>

<QuestionCard
  id="py-parse-03"
  number={39}
  question="What common pitfalls come up when using regular expressions to parse or clean ingested data?"
  difficulty="medium"
  topic="Regex"
>
```python
import re

pattern = re.compile(r"^\d{3}-\d{4}$")   # compile once, reuse across many rows
```

Common pitfalls: compiling the same pattern inside a loop (recompile once, outside the loop, for anything run per-row); using `.match()` (anchors at the start only) when you meant `.fullmatch()` or a pattern anchored with `^...$`; and reaching for regex on structured formats like JSON or CSV where a real parser handles edge cases (escaping, quoting, nested structures) that a hand-written pattern will eventually get wrong.
</QuestionCard>

<QuestionCard
  id="py-parse-04"
  number={40}
  question="Why can float arithmetic produce unexpected results, and when should you use Decimal instead?"
  difficulty="hard"
  topic="Numeric Precision"
>
```python
0.1 + 0.2  # 0.30000000000000004 — binary floating point can't represent 0.1 exactly

from decimal import Decimal
Decimal("0.1") + Decimal("0.2")  # Decimal('0.3') — exact
```

Floats use binary floating-point representation, which can't exactly represent most decimal fractions — fine for scientific/statistical data where tiny rounding error doesn't matter, but risky for money or anything requiring exact decimal arithmetic. Use `Decimal` (constructed from strings, not floats, to avoid importing the float's own imprecision) for financial calculations, and be explicit about rounding rules rather than relying on default float behavior.
</QuestionCard>
